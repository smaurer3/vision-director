What is Vision Director?

Vision Director is an automated camera-switching engine for live production environments such as church services, conferences, and live events. It watches your DSP (Digital Signal Processor) for microphone activity and, based on rules you define, tells your video switcher which camera to cut to — automatically, with configurable delays so fast transients are ignored.

The system connects everything via MQTT, a lightweight messaging protocol. Your ClearOne DSP publishes microphone gate events; Vision Director reads them, applies your rules, and publishes camera switch commands that Bitfocus Companion acts on to drive the ATEM switcher.

Quick Start

  1. Configure MQTT — Go to the Settings tab and enter your MQTT broker host, port, and credentials, then click Save & Reconnect. The dot in the header turns blue when connected.
  2. Add DSP Channels — Go to the DSP Channels tab and click + Add Channel for each microphone you want to track. Give each one a short Variable Name with no spaces — you'll use this name in rules.
  3. Check GHOLD values — Vision Director automatically queries each channel's hold time from the DSP. Wait a moment after saving a channel and you'll see the GHOLD column populate. Adjust Additional Hold if you want extra delay on top of what the DSP provides.
  4. Add Logic Rules — Go to the Logic tab and click + Add Rule. Choose Simple mode, pick which channels trigger the rule, set the edge, optionally block the rule when other channels are active, and enter the camera input number to switch to.
  5. Start the engine — Click the ENGINE button in the top-right until it shows RUNNING. The engine will now evaluate rules whenever a gate changes.
  6. Monitor live activity — Switch to the Monitor tab to watch gate states, pending triggers with countdown bars, and the switch log in real time.

DSP Channels

Each DSP Channel maps one microphone input on a ClearOne Converge 880 unit to a friendly variable name used in rules. Vision Director subscribes to gate events on the MQTT topic clearone/{device_id}/GATE/{channel} for each configured channel.

Field Reference

FieldDescription
Variable NameThe name used in logic rules and displayed throughout the UI. Use letters, numbers, and underscores — no spaces. Example: lectern_mic
Device IDThe identifier of the ClearOne unit. Selected from a dropdown that is automatically populated when you first open the DSP Channels tab — Vision Director sends a #** DID command to the DSP and lists every unit that responds. If no devices appear, check that the MQTT bridge is running and connected.
ChannelThe microphone channel number on the DSP, typically 1–8.
GHOLDThe Gate Hold time — how long the DSP keeps the gate open after audio stops. Queried automatically from the DSP on startup and when a channel is saved.
+ Hold (s)An Additional Hold time in seconds added on top of GHOLD. Use this to extend the debounce delay without changing DSP settings.
Total DelayGHOLD + Additional Hold. This is how long after a gate event the engine waits before checking conditions and firing a camera switch.
Tip: After saving a channel, Vision Director automatically queries the DSP for its GHOLD value over MQTT. If the GHOLD column shows —, use the ↻ refresh button next to that channel to request it again.

Logic Rules

A Logic Rule tells the engine: "when this microphone activity happens, switch to this camera." Each rule has a name, a target camera input number, a priority, and a mode.

Simple Mode

Simple mode uses checkboxes rather than expressions — no coding knowledge required.

FieldDescription
Trigger ChannelsAny checked channel will start this rule's timer when its gate changes on the selected edge. The delay used is the Total Delay of the specific channel that changed.
EdgeRising — fires when a gate turns ON (microphone becomes active). Falling — fires when a gate turns OFF (microphone goes silent). Use Rising to switch TO a camera, Falling to switch AWAY.
Blocked ByIf any checked channel is ON when the timer expires, the switch is cancelled. Use this to prevent a rule firing while a higher-priority mic is active — e.g. block Audience if Lectern is on.
Camera InputThe camera number published to the MQTT camera switch topic when the rule fires. Matches the input number on your ATEM switcher.
PriorityHigher numbers are evaluated first. When multiple rules could fire simultaneously, the highest priority rule wins.

Advanced Mode

Advanced mode lets you write boolean expressions using variable names directly, giving you full control over complex logic.

FieldDescription
Trigger ExpressionEvaluated on every gate change. If true, the delay timer starts. Example: (audience1 || audience2) && !lectern
Condition ExpressionOptional. Evaluated after the delay. If false, the switch is cancelled. Leave blank to recheck the trigger expression instead.
EdgeSame as Simple mode — Rising or Falling selects which type of gate change starts the timer.

Expression Operators

  • && — AND. Both sides must be true.
  • || — OR. Either side can be true.
  • ! — NOT. Inverts a value.
  • == / != — Equals / Not equals. Compare to 1 (on) or 0 (off).
Note: Variable names in expressions must exactly match the Variable Name set on each DSP Channel. Unknown variable names evaluate as false (off) rather than causing an error.

How the Delay Timer Works

Understanding the delay prevents unexpected behaviour during a live event.

  1. Gate event received — A microphone gate turns ON or OFF. The engine checks which rules match the changed channel and edge direction.
  2. Timer starts — For each matching rule, a countdown begins equal to the Total Delay of the channel that just changed. The pending trigger appears in the Monitor tab with a countdown bar.
  3. Recheck at expiry — When the timer expires the engine rechecks conditions. For a Rising rule: the triggering channel must still be ON. For a Falling rule: it must still be OFF. Any Blocked By channels must all be OFF.
  4. Switch fires (or cancels) — If all conditions pass, the camera switch command is published to MQTT and logged. If any condition fails, the trigger is silently cancelled.
Tip: Each trigger channel is independent. If Piano fires first (2 s delay) and Audience fires 1 s later (3 s delay), the engine keeps Piano's timer because it expires sooner — the switch still happens at Piano's original deadline. A new trigger only replaces the running timer if it would expire earlier.

Troubleshooting

SymptomWhat to check
MQTT dot is red / disconnectedVerify the broker host and port in Settings. Confirm the broker is running and reachable from the Raspberry Pi. Check username and password if authentication is required.
Device ID dropdown shows "No devices found"The dropdown is populated by a #** DID query sent when you open the DSP Channels tab. If it stays empty, check that the MQTT bridge is running, the broker host in Settings is correct, and the bridge is subscribed to clearone/discover. Navigate away and back to the DSP Channels tab to retry.
Gate cards never light upConfirm the ClearOne MQTT bridge is running and connected to the same broker. Check that the Device ID on each DSP Channel matches what the bridge is publishing.
GHOLD shows — and never populatesThe DSP must be online and the bridge must be forwarding GHOLD responses. Use the ↻ button to retry. Check that the bridge is subscribed to clearone/+/GHOLD/+/state.
Rules never fireCheck the engine button shows RUNNING. Confirm the rule is enabled (checkbox on the rule card). Watch the Monitor tab — if a pending trigger appears and then cancels, a Blocked By channel or recheck condition is failing.
Camera cuts happen but the switcher doesn't respondConfirm the Camera Switch Topic in Settings matches the topic Bitfocus Companion is subscribed to. Check the Switch Log to verify the rule is firing with the correct camera number.
Cuts are too slow or too fastAdjust the Additional Hold on the DSP Channel. Increase it to add more debounce, decrease it for a faster response. Remember Total Delay = GHOLD + Additional Hold.
